Project audit — 2 October 2026

The highest-priority problems are exploitable authorization failures, unauthenticated Shopify mutations, and OAuth credential disclosure. Fix these before query optimization or formatting work.

Scope: Accounts, EmailMarketing, Shopify integration, Python models/serializers/views/services, migrations, pixel JavaScript, settings, Docker build, seed scripts, and documentation. This is a source review with targeted isolated reproductions, not a penetration test of the deployed service. No application code was changed. No production database, email provider, or Shopify account was contacted. Production proxy rules, cloud permissions, actual database sizes/index plans, and frontend rendering were not available. Findings below distinguish confirmed behavior from deployment-dependent risks; this is not a guarantee that every possible issue has been discovered.

Severity: Critical = account takeover, public tenant data access, or secret disclosure; High = substantial security, delivery, or data-loss impact; Medium = correctness, reliability, or scaling problem; Low = maintainability or unnecessary code. Related manifestations are grouped rather than counted repeatedly.

Validation performed:

- All 78 Python files passed AST syntax parsing.
- Repository migrations ran successfully against an isolated in-memory SQLite database using explicitly configured audit settings. Project settings, environment credentials, and startup migration hooks were not loaded.
- An anonymous request to `CampaignRecipientsView` returned HTTP 200 and a recipient row.
- An unsigned customer webhook returned HTTP 200 and inserted a fabricated contact.
- A tenant administrator invited an unrelated superuser, then changed that superuser's password through `UserDetailView`: HTTP 200; the password change was verified.
- A campaign create serializer accepted another store's template ID.
- A mocked unsigned OAuth callback sent `client_secret` to `https://attacker.example/admin/oauth/access_token`. No network request was made.
- `recalculate_campaign_stats()` executed 12 SQL statements: 11 SELECTs and one UPDATE.
- `node --check shopify_integration/pixel_script.js` failed at line 87 with a duplicate `const` declaration.
- The installed Python SMTP SSL implementation defaults to an unverified context when no explicit context is supplied: hostname checking disabled and `CERT_NONE`.

Security and access-control findings:

1. **Critical — Existing-account takeover through invitations.** Locations: [invitation handling](Accounts/serializers.py#L240), [user editing](Accounts/views.py#L158). Any registered tenant admin can add an existing user to their own client without that user's acceptance. The admin can then edit the shared user's email, password, activity, and global role. There is no exclusion for staff/superusers. The superuser-password takeover was reproduced. **Solution:** implement expiring invitations requiring the existing user's acceptance; restrict tenant admins to membership attributes; move password/email changes into authenticated account-owner flows; block tenant control of privileged accounts. Audit existing memberships and revoke compromised credentials after fixing the path.

2. **Critical — Anonymous, cross-tenant campaign-recipient disclosure.** Locations: [recipient endpoint](EmailMarketing/Views/Campaigns.py#L396), [permission override](Accounts/mixins.py#L83). If the scoped campaign lookup fails, the endpoint falls back to `filter(id=campaign_id)` without a store. Combined with skipped permission enforcement, knowing/enumerating campaign IDs exposes names, emails, engagement, order IDs, order totals, and errors without authentication. Reproduced. **Solution:** remove the unscoped fallback; resolve only through an authorized store; enforce authentication and store permissions before lookup. Add anonymous and cross-tenant regression tests.

3. **Critical — Unsigned Shopify webhooks are accepted.** Location: [receiver](shopify_integration/webhooks.py#L242). HMAC is checked only when both the secret and signature header exist. Omitting the signature bypasses verification and allows contact/segment mutations for a supplied shop. A fabricated customer insertion was reproduced. **Solution:** reject missing secret/signature, verify the raw body before parsing or processing, require an exact registered shop, and explicitly allow supported topics.

4. **Critical — Public OAuth callback discloses app secrets to arbitrary hosts.** Locations: [host normalization](shopify_integration/views.py#L35), [callback exchange](shopify_integration/views.py#L177). `clean_domain()` accepts arbitrary dotted hosts; callback inputs choose a store and a destination, then the server POSTs the store/global app secret there. Callback HMAC is not verified. Reproduced with a mocked outbound request. This is also an SSRF entry point. **Solution:** validate a canonical `*.myshopify.com` hostname with no userinfo, port, path, or query; verify Shopify callback HMAC before any request; validate state; reject redirects/untrusted destinations. Rotate exposed app credentials if the vulnerable endpoint has been reachable.

5. **High — OAuth state does not bind shop ownership or the initiating user.** Locations: [install](shopify_integration/views.py#L123), [state creation](shopify_integration/views.py#L157), [callback](shopify_integration/views.py#L187). State is a predictable store ID; the public install route accepts any store ID. A callback can replace a store's integration without proving that the installer controls that local store. This remains a problem after host validation. **Solution:** use a cryptographically random, single-use, expiring server-side state record binding the authorized user, local store, and exact shop; verify every value before persisting tokens. Design unauthenticated merchant onboarding separately.

6. **High — Shared store permission implementation fails open.** Locations: [authentication mixin](Accounts/mixins.py#L9), [store mixin](Accounts/mixins.py#L83), [base class](EmailMarketing/Views/base.py#L5). Authentication and permission lists are empty, authentication exceptions are swallowed, and `StoreContextMixin.check_permissions()` never calls its parent. Consequently `HasStoreContext` and any future declared store permissions do not run. Many handlers merely return empty data or crash for `store=None`; this does not mean every endpoint exposes every store, but it directly enables finding 2. **Solution:** restore DRF authentication, explicitly require `IsAuthenticated`, raise on invalid client/store access, and call normal permission enforcement after context resolution.

7. **High — Authorization roles and store assignments are global instead of tenant-scoped.** Locations: [admin permission](Accounts/permissions.py#L9), [store resolver](Accounts/mixins.py#L102), [user serializer](Accounts/serializers.py#L86), [invitation updates](Accounts/serializers.py#L261). `ClientUser.role` exists but permissions use `User.user_type`; assignments accept `Store.objects.all()`. Editing a user in one client changes their role and can replace assignments across other clients. **Solution:** use the active membership's role and tenant-specific store grants; constrain all related-field querysets to the authorized client; validate membership before assigning a store; prevent tenant APIs from modifying shared global identity fields.

8. **High — Store reads bypass operator assignments.** Locations: [store list](Accounts/views.py#L199), [store detail](Accounts/views.py#L214), [store output](Accounts/serializers.py#L15). Any authenticated member can list/retrieve every store in their client even if the operator is assigned only one. Output includes each store's API key. **Solution:** apply the same assignment restriction used for store context; remove secrets from ordinary serializers and expose credential management only through a narrowly authorized flow. The store API key is not used for authentication anywhere in this repository, so no additional API-key takeover is assumed.

9. **High — Campaign template/segment relationships are not tenant-validated.** Locations: [campaign serializers](EmailMarketing/Serializer/CampaignSerializer.py#L33), [create serializer](EmailMarketing/Serializer/CampaignSerializer.py#L82), [build audience](EmailMarketing/Views/Campaigns.py#L290). ModelSerializer related fields accept global IDs; build-audience saves the first segment ID without ownership validation. Another store's template content or segment name/config can become reachable through a local campaign. Serializer acceptance was reproduced. **Solution:** scope related-field querysets to `request.store`, validate every segment ID, reject unknown/foreign IDs, and enforce the same invariant in service functions.

10. **High — Public pixel events can forge revenue and cross tenant boundaries.** Location: [pixel ingestion](shopify_integration/views_pixel.py#L76). If no valid execution token resolves, email-only lookup is global whenever the supplied store cannot be resolved. Anyone knowing an email can submit purchases/order totals and receive campaign/recipient IDs. Even with a token, browser-supplied purchase values are untrusted. **Solution:** remove global fallback, require exact store binding, use signed/scoped attribution identifiers, and obtain authoritative purchases/revenue from authenticated order webhooks. Validate event names, amounts, currency, timestamps, and order IDs; add abuse limits.

11. **High — Shopify credentials are returned in API responses.** Location: [settings serializer](shopify_integration/serializers.py#L4). Access tokens, refresh tokens, and custom app secrets are readable fields; `read_only` does not hide a field. **Solution:** make input secrets write-only, omit refresh tokens from responses entirely, return connection state/masked metadata, and restrict changes to tenant admins. Consider protected secret storage for the plaintext model fields in `shopify_integration/models.py:8`.

12. **High — Database password is printed during settings import.** Location: [settings](email_marketing_ms_django_backend/settings.py#L87). Worker/management-command startup prints the database password and username into logs. **Solution:** remove the print, redact secret-bearing errors, and rotate the password if those logs have been accessible outside the intended credential boundary.

13. **High — SMTP SSL does not explicitly verify the server certificate.** Location: [SMTP connection](EmailMarketing/BusinessLogic/EmailProvider.py#L21). `SMTP_SSL()` receives no `ssl.create_default_context()`. The installed runtime's default is unverified, exposing SMTP credentials/message content to a network interception scenario. The STARTTLS branch does pass a verifying context. **Solution:** pass `context=ssl.create_default_context()` to SMTP_SSL, require encryption, and test rejection of an untrusted certificate.

14. **High — Sender identity is not securely bound to a tenant's verified domain.** Locations: [identity changes](EmailMarketing/Views/SenderIdentity.py#L20), [provider](EmailMarketing/BusinessLogic/EmailProvider.py#L32), [dummy verification](EmailMarketing/BusinessLogic/SESService.py#L75). Custom `from_email` need not match `domain`; send ignores verification status; missing/dummy AWS credentials make domain validation return True. With a shared SES account, provider-level verification alone does not establish local tenant ownership. **Solution:** validate address/domain ownership and tenant binding, require a verified identity when sending, reserve unique platform sender identities, and allow mocks only in explicit test settings that cannot report production verification.

15. **High, deployment-dependent — Unsafe production defaults and image contents.** Locations: [settings](email_marketing_ms_django_backend/settings.py#L12), [Dockerfile](Dockerfile#L1). A known fallback secret, DEBUG enabled unless `production` is exactly `True`, wildcard hosts, global CORS, and absent application HTTPS/cookie hardening make misconfiguration dangerous. `COPY . .` has no `.dockerignore`, so local `.env`, databases, media, and Git metadata can enter image layers if present in the build directory. **Solution:** fail startup for missing production secrets, parse environment booleans explicitly, restrict hosts/origins, configure HTTPS at the trusted proxy/application boundary, add `.dockerignore`, and run as a non-root user. Actual deployed settings/proxy behavior were not inspected.

16. **Medium — Authentication revocation is delayed by cached credentials and authorization objects.** Locations: [auth cache](Accounts/mixins.py#L28), [context caches](Accounts/mixins.py#L48), [logout](Accounts/views.py#L78). Cached `(user, token)` survives token deletion; cached users/clients/stores bypass fresh activity and membership checks for up to 120 seconds. Password changes also leave the existing DRF token valid. **Solution:** avoid caching authenticated model instances, or use centrally versioned authorization records with revocation invalidation; revoke tokens on sensitive account changes and verify deactivated users cannot authenticate.

17. **Medium — Password policy and request abuse controls are incomplete.** Locations: [registration/invitation](Accounts/serializers.py#L158), [password edit](Accounts/views.py#L174), [REST configuration](email_marketing_ms_django_backend/settings.py#L127). Configured Django password validators are never called by these serializers; direct password edits have no minimum length. Login, registration, sends, imports, and public events have no in-repository throttles. **Solution:** call `validate_password()` in every password-setting flow; add appropriate authentication and per-tenant operation limits, with proxy controls as a complementary layer. External rate limiting may exist but was not available to review.

18. **Medium — Open redirect and tracking-token exposure.** Locations: [click redirect](EmailMarketing/Views/Tracking.py#L62), [URL instrumentation](EmailMarketing/BusinessLogic/BulkEmailSender.py#L264). The redirect accepts arbitrary destinations even without a token. The sender adds the same token used for unsubscribe to every non-excluded link, including external sites, and naïve concatenation places parameters after URL fragments. **Solution:** use signed link IDs mapped to approved campaign URLs, separate unsubscribe capability from analytics identifiers, and build URLs with URL parsing/query utilities. Do not assume UUID secrecy after placing it in third-party URLs.

19. **Medium — Media and personalization accept active content without adequate validation.** Locations: [media upload](EmailMarketing/Views/Media.py#L85), [renderer](EmailMarketing/BusinessLogic/TemplateRenderer.py#L29). Uploads trust extensions/types and accept arbitrary SVG; contact/personalization values and preview text are injected into HTML without escaping. Contact data arriving through integrations can alter email content. Browser XSS impact depends on how the frontend and media origin render it. **Solution:** validate actual file signatures, type/size/count limits and filenames; reject or sanitize SVG; use a separate media origin; escape ordinary personalization and explicitly allow only trusted HTML fields.

20. **Medium — Known development accounts can be created/reset in production.** Location: [seed script](seed_db.py#L15). The seed script creates a superuser with a fixed password and resets existing demo-user passwords without a development-only guard. **Solution:** refuse execution outside explicit development/test settings, generate credentials rather than embedding them, and never reset existing privileged accounts as a seed side effect. Presence of this script does not prove these accounts exist in production.

21. **High — Unsupported Django pin and stale integration API pins.** Locations: [requirements](requirements.txt#L1), [Shopify requests](shopify_integration/sync.py#L141), [webhook API](shopify_integration/webhooks.py#L49), [container runtime](Dockerfile#L1). Django is pinned to 4.1.2, below later security fixes and on an unsupported release line. Shopify requests repeatedly hardcode `2023-04` while app webhook configuration uses `2026-07`. **Solution:** migrate to a supported Django line and compatible dependencies/runtime, audit resolved dependencies, and centralize/test a supported Shopify API version. Unsupported Shopify versions can fall forward rather than execute the version written in the URL. Sources: [Django support table](https://www.djangoproject.com/download/), [Django 4.1.13 security release](https://www.djangoproject.com/weblog/2023/nov/01/security-releases/), [Shopify versioning](https://shopify.dev/docs/api/usage/versioning). No complete dependency/CVE scan was performed.

Delivery, data integrity, and correctness findings:

22. **High — Sending ignores current consent and suppression records.** Locations: [audience branches](EmailMarketing/BusinessLogic/BulkEmailSender.py#L46), [send loop](EmailMarketing/BusinessLogic/BulkEmailSender.py#L132), [CSV consent overwrite](EmailMarketing/Views/Campaigns.py#L647), [contact importer](Accounts/BusinessLogic/CsvContactImporter.py#L124). `specific_emails` skips opt-in filtering; all-contact/default branches skip `EmailUnsubscribe`; the send loop never rechecks consent after audience creation. CSV paths can change existing unsubscribed contacts back to subscribed. **Solution:** apply one suppression/consent policy across every audience path and again at send time; preserve existing opt-outs on imports unless an explicit, recorded resubscription occurs. Keep independent suppression evidence rather than relying only on a mutable Boolean.

23. **High — Concurrent sends can deliver duplicate emails.** Locations: [send endpoint](EmailMarketing/Views/Campaigns.py#L327), [resume](EmailMarketing/Views/Campaigns.py#L361), [batch selection](EmailMarketing/BusinessLogic/BulkEmailSender.py#L121). Status checking and worker start are not atomic; workers SELECT the same Pending recipients before either claims them. Resume can start another worker even while Sending. **Solution:** use an atomic campaign transition, durable unique job/lease, and transactional recipient claims (`select_for_update` where supported or conditional updates). Use provider idempotency where available; plain SMTP cannot guarantee exactly-once delivery across a crash after acceptance.

24. **High — Background threads have no durable recovery.** Locations: [thread helper](EmailMarketing/BusinessLogic/threading_utils.py#L6), [Shopify background work](shopify_integration/sync.py#L422), [sender](EmailMarketing/BusinessLogic/BulkEmailSender.py#L133). Worker restarts kill/interrupt jobs; crashed InProcess recipients are never reclaimed. Rendering occurs outside the send try/except, and finalization only tests Pending, so incomplete work may be misclassified as Sent. Shopify daemon threads likewise lose work and some lack database-connection cleanup. **Solution:** adopt a durable queue, persisted job state, leases/retries/backoff, heartbeat/timeout recovery, and explicit ambiguous-delivery handling. Finalization must account for InProcess, failed, and suppressed recipients.

25. **High — Campaign state and recipient history remain mutable during/after delivery.** Locations: [detail serializer](EmailMarketing/Serializer/CampaignSerializer.py#L53), [recipient upload](EmailMarketing/Views/Campaigns.py#L603), [audience build](EmailMarketing/BusinessLogic/BulkEmailSender.py#L62). Clients can PATCH status directly; CSV upload deletes all existing recipients regardless of campaign status and recreates them without an enclosing transaction. Audience rebuilding only appends and does not remove recipients from an old selection. **Solution:** make lifecycle status read-only, enforce a single transition service, permit audience replacement only in an editable state, and validate/stage replacements before an atomic swap. Freeze delivery snapshots and preserve historical recipient records.

26. **High — Full Shopify resync deletes campaign history before fetching replacement data.** Locations: [customer resync](shopify_integration/sync.py#L135), [recipient foreign key](EmailMarketing/models.py#L111), [segment resync](shopify_integration/sync.py#L338). Deleting contacts cascades into campaign recipients and their tracking history; API failure then leaves missing data. Segment resync deletes all nondefault segments, including potentially local ones, and nulls campaign segment links. **Solution:** upsert by stable external ID, stage successful snapshots before reconciliation, distinguish imported/local records, and soft-delete or preserve historical foreign-key targets.

27. **High — Contact signals generate duplicate Shopify updates and potential webhook feedback loops.** Locations: [contact signal](shopify_integration/signals.py#L7), [consent loop](shopify_integration/sync.py#L532), [unsubscribe](EmailMarketing/Views/Unsubscribe.py#L40), [webhook upsert](shopify_integration/webhooks.py#L277). Every linked-contact save triggers an outbound update even when consent did not change. Explicit consent/unsubscribe functions also send updates. An inbound Shopify customer update can trigger another outbound update, which may generate another webhook. **Solution:** move synchronization into an explicit consent-change service/outbox, track event origin, compare changed fields, and enqueue only after commit. Do not perform network side effects on every generic model save.

28. **High — Sync temporarily disables signals for the entire process.** Location: [customer sync](shopify_integration/sync.py#L130). `post_save.disconnect()` affects concurrent requests and other stores, not just the current import. Concurrent syncs can reconnect too early; deletion/initialization errors before reconnection can leave it disabled. **Solution:** remove process-global signal toggling; use explicit import operations without outbound side effects, or a carefully scoped origin mechanism. A `finally` alone does not solve the concurrency problem.

29. **High — Empty/failed Shopify segments can become all-subscriber audiences.** Locations: [membership fallback](shopify_integration/sync.py#L278), [audience filter](EmailMarketing/BusinessLogic/AudienceResolver.py#L26). Empty `member_emails` is treated as no filter, rather than an empty membership. Unsupported Shopify query text falls back to every local contact; the substring `subscribed` also matches `unsubscribed`. Failures are indistinguishable from legitimate empty results. **Solution:** represent empty membership explicitly, fail closed for failed/unsupported evaluations, retain last successful snapshot with stale/error state, and avoid approximating arbitrary Shopify queries with substring checks.

30. **Medium — Shopify pagination is incomplete.** Locations: [member query](shopify_integration/sync.py#L240), [segment query](shopify_integration/sync.py#L350), [webhook listing](shopify_integration/webhooks.py#L62). Only the first 250 segment members and first 100 segments/subscriptions are fetched; no cursor traversal exists. **Solution:** request `pageInfo`, iterate cursors with bounded retries, and only publish the new membership snapshot after the complete traversal. This can silently omit recipients even when the first page succeeds.

31. **Medium — Domain and external-record matching are ambiguous.** Locations: [webhook store lookup](shopify_integration/webhooks.py#L229), [privacy verifier](shopify_integration/views.py#L460), [segment upsert/delete](shopify_integration/webhooks.py#L311), [models](shopify_integration/models.py#L7). Domain lookup uses substring matching plus `.first()` and the domain is not unique. Segments are keyed/deleted by mutable names instead of Shopify IDs; customer sync keys by email instead of stable external ID. **Solution:** define exact canonical domain ownership, add suitable uniqueness constraints, and upsert external records using `(store, external_id)` with explicit rename/email-change handling. Resolve existing duplicates before migrations.

32. **Medium — Purchase/event storage loses information and races.** Location: [pixel event mutations](shopify_integration/views_pixel.py#L130). A recipient has only one order ID/total; later orders overwrite earlier purchases. Read-increment-save counters lose concurrent increments, and retries duplicate page/cart/checkout counts. There is no unique event/order ledger. **Solution:** persist deduplicated events/orders with unique external IDs, use atomic `F()` increments where appropriate, aggregate monetary values by currency, and define attribution/replay rules. Use `now - sent_at > timedelta(days=7)` rather than `elapsed.days > 7`, which admits nearly eight days; reject attribution to unsent recipients.

33. **Medium — Delivery and engagement share a conflicting status field.** Locations: [sender counters](EmailMarketing/BusinessLogic/BulkEmailSender.py#L170), [click tracking](EmailMarketing/Views/Tracking.py#L75), [open tracking](EmailMarketing/Views/Tracking.py#L35). Opened/Clicked/Purchased recipients stop counting as Sent in the sender; clicks overwrite Purchased or Unsubscribed status; a Pending recipient can become Opened and disappear from the sending queue. Click handling also checks `not opened_at` after setting it, so that counter-update branch never executes. **Solution:** separate delivery state from engagement/consent events, count delivered mail using `sent_at`, and perform conditional atomic first-event updates.

34. **Medium — Scheduling is represented but not implemented.** Locations: [campaign schedule field](EmailMarketing/models.py#L89), [send endpoint](EmailMarketing/Views/Campaigns.py#L335), [task stub](EmailMarketing/tasks.py#L1). No scheduler dispatches due campaigns and sending does not honor future `scheduled_at`. **Solution:** implement scheduled durable jobs with cancellation and timezone-aware timestamps, or reject scheduling input until supported. Use aware UTC persistence and convert at the UI boundary; current settings use naive Asia/Karachi time.

35. **High for databases containing existing template data — Migrations drop and recreate template columns.** Locations: [migration 0006](EmailMarketing/migrations/0006_remove_emailtemplate_editor_json_and_more.py#L11), [migration 0007](EmailMarketing/migrations/0007_emailtemplate_editor_json_emailtemplate_is_system_and_more.py#L11). `editor_json`, `is_system`, `preview_text`, and `subject` are removed then re-added. Existing contents are lost when upgrading through these migrations. **Solution:** audit affected deployments/backups; restore lost data where possible. For an unapplied upgrade path, design a data-preserving migration replacement/bridge after checking migration history; do not casually rewrite already-applied shared migrations.

36. **Medium — Privacy webhooks acknowledge work they never perform.** Location: [privacy handler](shopify_integration/views.py#L491). Data requests and redactions only print messages and return success; there is no deletion/export queue or completion record. **Solution:** durably record validated requests, implement tenant-scoped export/deletion with defined retention handling, and track completion/retry status. This is a functional observation, not a determination of legal compliance.

37. **Medium — The provided pixel script does not parse.** Locations: [first declaration](shopify_integration/pixel_script.js#L3), [duplicate declaration](shopify_integration/pixel_script.js#L87). Two complete versions declare the same top-level `const`; the whole file fails before subscriptions run. Merely renaming one would leave duplicate subscriptions. **Solution:** keep one implementation and one subscription per event; run syntax validation and integration checks. Pass event context explicitly rather than assuming sandbox `window.location` is the storefront URL; verify that behavior in the intended Shopify pixel environment.

38. **Medium — Campaign HTML edits are silently ignored.** Location: [campaign detail serializer](EmailMarketing/Serializer/CampaignSerializer.py#L40). `html_content` is a read-only `SerializerMethodField`; create accepts it but ordinary PATCH/PUT does not update it. **Solution:** make the stored HTML writable with validation and expose computed fallback HTML separately, or explicitly implement validated update behavior.

39. **Medium — Sender identity configuration has correctness and atomicity defects.** Locations: [SES region](EmailMarketing/BusinessLogic/SESService.py#L17), [identity creation](EmailMarketing/Views/SenderIdentity.py#L30), [identity model](EmailMarketing/models.py#L155). `AWS_SES_REGION_NAMEE` is misspelled, ignoring the configured region. The view creates identity/store changes before validating custom-domain inputs; concurrent requests can create multiple active identities because no uniqueness constraint backs `get_or_create`. **Solution:** correct the setting, validate complete input first, use an atomic service, and enforce one active identity per store using a database-compatible constraint/design. Align SES verification and SMTP regions.

40. **Medium — Manual input parsing causes avoidable 500s and unsafe defaults.** Locations: [contact pagination](Accounts/views.py#L256), [campaign pagination](EmailMarketing/Views/Campaigns.py#L72), [segment pagination](EmailMarketing/Serializer/AudienceSerializer.py#L47), [ordering](EmailMarketing/Views/Campaigns.py#L485), [unsubscribe token](EmailMarketing/Views/Unsubscribe.py#L19), [consent input](Accounts/views.py#L299). Zero/negative page sizes can divide by zero or produce invalid slices; huge sizes are unbounded. Arbitrary ORM ordering can raise errors or request expensive relation sorts. Invalid UUIDs are uncaught in unsubscribe, and an empty consent selection means the entire store. **Solution:** use typed serializers and standard bounded pagination, allowlist ordering, validate UUIDs, and require an explicit all-contacts flag rather than interpreting empty selections as all. ORM ordering here is not evidence of SQL injection.

41. **Medium — Contact imports overwrite unrelated information and can partially commit.** Locations: [CSV defaults](Accounts/BusinessLogic/CsvContactImporter.py#L129), [bulk API](Accounts/views.py#L338), [campaign CSV](EmailMarketing/Views/Campaigns.py#L537). Missing CSV columns become blank/zero values overwriting existing names/spend; row-by-row validation can fail after earlier writes. Campaign CSV strips header names but retains original row keys, breaking whitespace-padded headers; case-normalization differs across import paths. **Solution:** distinguish missing from explicitly empty values, normalize identifiers consistently, validate/stage first, write in bounded transactions, and return precise row-level results. Reject non-finite/oversized numeric values and enforce model lengths before writes.

42. **Medium — Derived audience data is inconsistent.** Locations: [audience breakdown](EmailMarketing/BusinessLogic/AudienceResolver.py#L81), [segment update](EmailMarketing/Views/Audiences.py#L86), [segment detail](EmailMarketing/Serializer/AudienceSerializer.py#L42), [customer sync](shopify_integration/sync.py#L186). `inactive = total - repeat_buyers - new_customers` is always zero because order counts partition those two groups. Dynamic segment details show members only from stored email lists; updates do not recalculate cached counts. Shopify sync does not populate `last_order_at` or tags used by advertised filters. **Solution:** define inactivity by timestamps, use the same resolver for estimate/detail/build, update derived counts asynchronously, and populate the source fields needed by supported filters.

43. **Medium — SQLite development configuration cannot execute the JSON tag filter.** Locations: [tag filter](EmailMarketing/BusinessLogic/AudienceResolver.py#L30), [default database](email_marketing_ms_django_backend/settings.py#L102). `JSONField` containment lookups used here are unsupported by Django's SQLite backend, so tag audiences fail on the documented default environment. **Solution:** test with the production database engine, normalize tags into related rows, or implement an explicitly supported backend-specific representation. Avoid loading an entire contact table into Python as a workaround.

44. **Medium — Integration errors are swallowed or reported as success.** Locations: [Shopify consent update](shopify_integration/sync.py#L456), [bulk result](shopify_integration/sync.py#L551), [media result](EmailMarketing/Views/Media.py#L118), [webhook result shape](shopify_integration/webhooks.py#L45). Consent APIs count local saves and claim Shopify synchronization even when remote calls fail. Failed uploads can return HTTP 201 with an empty result. Webhook registration returns two values for missing configuration, while the caller unpacks four. **Solution:** return typed, consistent result objects; distinguish queued/local/remote outcomes; persist retryable failures; give client-safe errors and structured internal logs. Do not return raw upstream bodies or exceptions to callers.

Heavy queries, unnecessary work, and resource usage:

45. **High at scale — Every pixel event rescans the entire campaign repeatedly.** Locations: [statistics recalculation](EmailMarketing/Views/Campaigns.py#L192), [pixel calls](shopify_integration/views_pixel.py#L141), [detail GET](EmailMarketing/Views/Campaigns.py#L246). Recalculation performs seven separate counts, four SUM aggregates, and one UPDATE: 12 statements, measured in isolation. It runs for every recognized storefront event and campaign-detail GET. For a campaign with N recipients and E events, repeated aggregation grows roughly with E×N work; exact plan costs depend on indexes/database. **Solution:** combine counts/sums into one filtered aggregate as an immediate improvement; use deduplicated atomic event updates and asynchronous reconciliation for high traffic. GET should read stored/cached statistics rather than write them.

46. **Medium — Sending performs two avoidable SELECTs per recipient and reconnects SMTP every time.** Locations: [batch loading](EmailMarketing/BusinessLogic/BulkEmailSender.py#L121), [context builder](EmailMarketing/BusinessLogic/TemplateRenderer.py#L60), [identity lookup](EmailMarketing/BusinessLogic/EmailProvider.py#L32), [SMTP lifetime](EmailMarketing/BusinessLogic/EmailProvider.py#L89). `select_related('contact')` omits `contact__store`, so rendering fetches each contact's store. Each send fetches the same identity again, then connects/authenticates/quits SMTP. **Solution:** pass the already-loaded campaign store, preload one verified identity per job/batch, reuse bounded SMTP sessions with reconnect logic, and batch safe recipient status writes without weakening recipient claims. For 10,000 recipients, these two repeated lookups alone imply roughly 20,000 avoidable SELECTs before other work.

47. **Medium — Campaign counts are repeatedly recomputed per batch.** Locations: [batch counters](EmailMarketing/BusinessLogic/BulkEmailSender.py#L170), [final counters](EmailMarketing/BusinessLogic/BulkEmailSender.py#L186), [tracking counters](EmailMarketing/Views/Tracking.py#L40). 48. **Medium — Bulk imports and consent updates are actually per-row work.** Locations: [CSV upsert](Accounts/BusinessLogic/CsvContactImporter.py#L147), [bulk API](Accounts/views.py#L343), [Shopify import](shopify_integration/sync.py#L186), [campaign import](EmailMarketing/Views/Campaigns.py#L608), [consent loop](shopify_integration/sync.py#L532). 49. **Medium — Membership and user serialization contain N+1 query patterns.** Locations: [membership resolver](Accounts/mixins.py#L63), [client access response](Accounts/serializers.py#L122), [user list](Accounts/views.py#L147). 50. **Medium — Unbounded lists and buffered imports amplify memory and response size.** Locations: [REST settings](email_marketing_ms_django_backend/settings.py#L127), [template list](EmailMarketing/Views/Templates.py#L8), [media list](EmailMarketing/Views/Media.py#L60), [recipient build](EmailMarketing/BusinessLogic/BulkEmailSender.py#L62), [CSV buffering](EmailMarketing/Views/Campaigns.py#L534). 51. **Medium — Segment membership is duplicated as both JSON emails and relational rows.** Locations: [segment sync](shopify_integration/sync.py#L394), [contact segment filter](Accounts/views.py#L249), [segment detail](EmailMarketing/Serializer/AudienceSerializer.py#L38). 52. **Medium — Redundant audience counts and unnecessary DISTINCT.** Locations: [estimate endpoint](EmailMarketing/Views/Audiences.py#L111), [breakdown](EmailMarketing/BusinessLogic/AudienceResolver.py#L69), [stats](EmailMarketing/Views/Campaigns.py#L199). 53. **Medium — Database indexing needs cleanup and targeted query-plan validation.** Locations: [store/contact indexes](Accounts/models.py#L42), [recipient indexes](EmailMarketing/models.py#L130), [recipient ordering](EmailMarketing/Views/Campaigns.py#L490), [Shopify external ID updates](shopify_integration/sync.py#L473). 54. **Medium — No default HTTP timeouts, backoff, or bounded integration concurrency.** Locations: [request wrapper](shopify_integration/sync.py#L64), [OAuth exchange](shopify_integration/views.py#L205), [refresh](shopify_integration/sync.py#L37), [synchronous segment sync](shopify_integration/views.py#L347). 55. **Medium — Cache invalidation is incomplete and process-local.** Locations: [campaign cache helpers](EmailMarketing/Views/Campaigns.py#L29), [campaign mutations](EmailMarketing/Views/Campaigns.py#L240), [segment cache](EmailMarketing/Views/Audiences.py#L18), [settings](email_marketing_ms_django_backend/settings.py#L127), [workers](Dockerfile#L7). 56. **Medium — Webhook processing does slow work inline and recreates subscriptions unnecessarily.** Locations: [registration loop](shopify_integration/webhooks.py#L85), [segment webhook](shopify_integration/webhooks.py#L296). Recommended execution order:

1. Block public exploit paths: account takeover, unscoped recipients, unsigned webhooks, arbitrary-host OAuth, and missing permission enforcement (1–6). Review logs and rotate credentials according to actual exposure.
2. Restore tenant invariants, credential hygiene, and consent enforcement (7–17, 22).
3. Introduce durable job/event processing, safe campaign transitions, and nondestructive sync (23–36, 54–57).
4. Fix confirmed functional failures: pixel parsing, ignored HTML edits, SES setting typo, malformed input behavior, segment correctness, import errors, and unsubscribe-link corruption (37–44, 63).

Useful acceptance checks for the remediation:

- Anonymous and wrong-tenant access consistently fails before database mutation or sensitive serialization.
- A client admin cannot mutate an unrelated/shared user's credentials or platform privilege.
- Missing/invalid webhook signatures and invalid OAuth state/HMAC never cause outbound requests or writes.
- Two simultaneous send requests do not claim the same recipient; restart recovery preserves delivery history.
- Opted-out contacts stay suppressed after imports, queued-audience creation, and Shopify sync.
- Pixel retries and multiple purchases preserve accurate, deduplicated event/order totals.
- One statistics reconciliation uses one aggregate SELECT and at most one UPDATE; event ingestion does not synchronously rescan every recipient.
- Imports use bounded memory, preserve absent fields, and report partial/remote failures accurately.
- JavaScript syntax, migration upgrade/data-preservation tests, tenant isolation tests, and database-specific query tests run in CI.
